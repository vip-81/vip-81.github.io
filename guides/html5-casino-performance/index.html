HTML5 賭場遊戲效能：Canvas、Web Audio、記憶體洩漏與除錯

「在我的電腦很順」不是效能結論。這篇建立一個可測量的流程：先設定幀率與記憶體預算，再處理 Canvas 解析度、離屏快取、時間步、音訊解鎖、背景暫停與 context lost，最後用 DevTools 找出真正的瓶頸。

先說結論

先量測，再優化。Canvas 依 devicePixelRatio 放大但設定上限；靜態背景與符號用離屏快取；邏輯用固定時間步，渲染可插值；Web Audio 在第一個手勢解鎖；切到背景要停止或降頻；每個監聽器、計時器與紋理都要有 cleanup。效能的敵人通常是配置與佈局，而不是「Canvas 本身」。

先定預算：幀率、互動延遲與記憶體

沒有預算就沒有優化。對賭場遊戲，建議至少定三個指標：

  • 幀率：中階手機 60fps，低階手機不低於 45fps；掉到 30fps 時要能降級而不是卡死。
  • 互動延遲：按下旋轉到第一幀動畫小於 100ms；音效小於 50ms。
  • 記憶體：連續玩 30 分鐘，JS heap 不應持續線性上升；單一 Canvas 不超過裝置可承受的尺寸。

用 performance.mark() 與 performance.measure() 標記「按下按鈕 → 開始動畫 → 結算」的區間，比只看 FPS 更能找出使用者感受到的延遲。FPS 高但按下後 300ms 才反應，仍然是不及格。

Canvas 解析度：devicePixelRatio 與上限

Canvas 的 width／height 是繪圖緩衝尺寸，CSS 的 width／height 是顯示尺寸。若 CSS 是 400×400、DPR 是 3，緩衝應為 1200×1200；否則瀏覽器會把 400×400 拉伸，看起來模糊。

function fitCanvas(canvas, maxDpr = 2) {
  const rect = canvas.getBoundingClientRect();
  const dpr = Math.min(window.devicePixelRatio || 1, maxDpr);
  const width = Math.max(1, Math.round(rect.width * dpr));
  const height = Math.max(1, Math.round(rect.height * dpr));
  if (canvas.width !== width || canvas.height !== height) {
    canvas.width = width;
    canvas.height = height;
  }
  const ctx = canvas.getContext("2d");
  ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
  return { ctx, width: rect.width, height: rect.height, dpr };
}

為什麼要設 maxDpr = 2？因為 3× 或 4× 的緩衝面積是 2× 的 2.25–4 倍，記憶體與填充率都會暴增，但肉眼差異有限。可以依裝置記憶體或 fps 動態調整，但不要讓 DPR 無上限。

用 ResizeObserver 監聽容器尺寸，而不是只聽 window.resize；行動瀏覽器的網址列收合、鍵盤彈出與旋轉都可能改變可用高度。重設 canvas.width 會清空內容與狀態，請在之後重新設定 transform 與快取。

離屏快取：只重畫會動的東西

賭場遊戲有大量靜態元素：賭桌絨布、輪盤底盤、背景漸層、標題、按鈕。這些不需要每幀重畫。把它們畫到離屏 canvas，主迴圈只 drawImage 一次，通常就能省下可觀的填充率。

const bg = document.createElement("canvas");
bg.width = LOGICAL_W; bg.height = LOGICAL_H;
const bctx = bg.getContext("2d");
drawTableBackground(bctx);

function render() {
  ctx.clearRect(0, 0, LOGICAL_W, LOGICAL_H);
  ctx.drawImage(bg, 0, 0);
  drawFish(ctx);
  drawBullets(ctx);
  drawHud(ctx);
}

注意：若背景會隨著視窗比例改變，快取就要重畫；若只是翻譯或主題切換，也要失效重建。不要快取「會整體旋轉的輪盤」再旋轉那張圖，因為額外的合成與取樣可能比直接畫 37 個扇形更慢，還會模糊。

固定時間步與背景暫停

requestAnimationFrame 的 delta 不穩定：120Hz 螢幕、背景切換、GC 都會讓它跳動。若直接把 delta 乘上速度，魚或滾輪可能瞬移，碰撞也可能穿透。用固定步長與累加器，讓邏輯可重播：

const STEP = 1 / 60;
let acc = 0;
let last = performance.now();

function loop(now) {
  const delta = Math.min(0.05, (now - last) / 1000);
  last = now;
  acc += delta;
  while (acc >= STEP) {
    update(STEP);
    acc -= STEP;
  }
  render(acc / STEP);
  requestAnimationFrame(loop);
}

切到背景時，瀏覽器會暫停 rAF，但音訊與計時器不一定停。請監聽 visibilitychange：document.hidden 為 true 時停止生成、暫停音效、記錄時間；回來時把 last 重設為 performance.now()，避免一次補上幾十秒的 delta。若遊戲有倒數，應以伺服器時間為準，而不是背景被凍結的 setTimeout。

DOM 與 Canvas 的分工

不是所有東西都該畫在 Canvas。餘額、投注、按鈕、結果文字、FAQ 用 DOM 更合適：可選取、可被螢幕閱讀器讀取、可用 CSS 響應式。Canvas 只負責遊戲視覺與粒子。混合架構的關鍵是「不要每幀改 DOM」：

  • 文字只在資料變動時更新，不要每幀寫 textContent。
  • 用 classList.toggle 取代重複設定 style。
  • 批次讀取幾何資訊，再批次寫入，避免 layout thrashing。
  • 清單用 DocumentFragment 或 replaceChildren，不要逐筆插入造成多次 reflow。

若卡牌或面板有大量動畫，考慮用 transform 與 opacity，這兩個屬性通常只觸發合成。避免動畫 top、left、width、height，因為會觸發佈局。

Web Audio：iOS 解鎖與節流

iOS Safari 要求音訊由使用者手勢啟動。最穩的做法是監聽第一個 pointerdown 與 keydown，在事件中建立或 resume() AudioContext，成功後移除監聽：

let ctx;
let unlocked = false;

async function unlockAudio() {
  if (unlocked) return true;
  ctx ??= new (window.AudioContext || window.webkitAudioContext)();
  if (ctx.state === "suspended") await ctx.resume();
  unlocked = ctx.state === "running";
  return unlocked;
}

window.addEventListener("pointerdown", unlockAudio, { once: true, capture: true });
window.addEventListener("keydown", unlockAudio, { once: true, capture: true });

不要在頁面載入時就播放聲音，也不要在每次點擊都建立新的 AudioContext。連續命中時，限制同時播放的節點數量，或重用同一個 buffer；否则音效會變成噪音，還會拖慢主執行緒。靜音時不要只是把 gain 設為 0，應停止排程新音效，節省 CPU。

WebGL context lost 與 Canvas 失敗

若使用 WebGL，必須處理 context lost。GPU 資源可能因驅動更新、記憶體不足或背景切換被回收：

canvas.addEventListener("webglcontextlost", (event) => {
  event.preventDefault();       // 允許之後恢復
  running = false;
  showNotice("圖形資源中斷，正在恢復…");
}, false);

canvas.addEventListener("webglcontextrestored", () => {
  rebuildTextures();
  rebuildBuffers();
  rebuildShaders();
  running = true;
}, false);

恢復後要重建所有 GPU 資源，不能沿用舊的 texture 或 buffer。Canvas 2D 不會有 context lost，但過大的 canvas（例如 DPR 4× 的 4K 畫布）可能配置失敗或變成空白；請設定尺寸上限並在失敗時降級。

記憶體洩漏：最常見的五個來源

  1. 事件監聽器：每次建立遊戲都 addEventListener，卻沒有在離開時移除。用 AbortController 一次清理。
  2. 計時器：setInterval 持續執行，即使畫面已卸載。保存 ID 並在 cleanup 中 clearInterval。
  3. 閉包：回呼捕獲了整個 state 或 DOM，導致無法回收。只捕獲需要的變數。
  4. 影像與 Canvas：不断建立新 Image／canvas 而沒有釋放。重用或設為 null 讓 GC 回收。
  5. 只增不減的陣列：粒子、歷史紀錄、訊息列表沒有上限。設定最大長度並淘汰舊資料。
const controller = new AbortController();
window.addEventListener("resize", onResize, { signal: controller.signal });
document.addEventListener("visibilitychange", onVisibility, { signal: controller.signal });

function destroy() {
  controller.abort();
  cancelAnimationFrame(rafId);
}

用 DevTools 的 Memory 面板取兩次 snapshot，比對 detached DOM 與 listener 數量；Performance 面板錄製 30 秒，觀察 GC 是否頻繁、long task 是否集中在結算或建立 DOM。

實測流程：不要靠感覺

  1. 用中階 Android 與 iPhone Safari 各測一次，不要只在桌機 Chrome。
  2. 開啟 4× CPU 節流，模擬低階裝置；觀察互動延遲與掉幀。
  3. 錄製 Performance，找出最長的 task 與強制同步佈局。
  4. 玩 10 分鐘，檢查 heap 與 listener 是否持續上升。
  5. 切到背景 30 秒再回來，確認時間步與音效沒有補播或爆音。
  6. 開啟「減少動態」，確認動畫縮短但結果仍正確。

把量測結果寫進 PR 或 issue，而不是只說「優化了」。例如「iPhone 12 Safari，旋轉到首幀 82ms，平均 58fps，10 分鐘 heap 從 18MB 到 21MB」比「感覺很順」有用得多。

行動端效能檢查表

  • Canvas 是否依 DPR 放大？是否設定上限？resize 後是否重設 transform？
  • 靜態背景與符號是否快取？是否避免每幀重建路徑與漸層？
  • 是否使用固定時間步？delta 是否有上限？背景回來是否重設 last？
  • 是否只在資料變動時更新 DOM？是否避免每幀讀寫幾何？
  • Web Audio 是否由手勢解鎖？是否限制同時播放數？
  • WebGL 是否處理 context lost／restored？Canvas 是否有尺寸上限？
  • 事件監聽、計時器、rAF、影像是否都有 cleanup？
  • 是否在真實手機與減少動態模式下測試？

常見問題

為什麼 Canvas 在高解析螢幕上會模糊？

因為 canvas 的 width/height 是邏輯像素，不是裝置像素。若 CSS 尺寸是 400×400、devicePixelRatio 是 3，實際需要 1200×1200 的繪圖緩衝；只設 400×400 會被拉伸而模糊。正確做法是依 DPR 放大內部尺寸，再用 ctx.setTransform 縮放繪製座標。

iOS Safari 為什麼沒有聲音？

Web Audio 必須由使用者手勢（點擊、按鍵）解鎖。請在第一個 pointerdown 或 keydown 時建立或 resume AudioContext，並在之後的播放函式中檢查 state。僅在頁面載入時建立 context 通常會處於 suspended。

什麼是 WebGL context lost？

GPU 資源可能因驅動、記憶體或背景切換而被回收，瀏覽器會發出 webglcontextlost 事件。應先 preventDefault 阻止預設行為，停止渲染，等 webglcontextrestored 後重建紋理、緩衝與著色器。Canvas 2D 不會有這個事件，但可能因尺寸過大而失敗。

為什麼遊戲玩久了越來越卡？

常見原因是事件監聽器、計時器、Canvas 或 Image 物件沒有釋放，或陣列只增不減。每次建立動畫或連線都要有對應的 cleanup；用 Chrome DevTools 的 Memory 與 Performance 面板觀察 heap 與 listener 數量是否持續上升。

要不要用 will-change 或 translateZ 加速？

只在確實有效的地方使用。對大量元素濫用 will-change 會增加記憶體與合成成本，反而更慢。Canvas 遊戲通常不需要；若是 DOM 卡牌或面板動畫，先量測再局部提升。
