捕魚機 AI 與碰撞：魚群路徑、物件池、砲台倍率與伺服器結算

捕魚機是即時系統：幾十條魚、數百顆子彈、連續的命中特效與音效同時發生。這篇從座標與時間步開始，拆解魚群行為、生成與回收、碰撞與穿透修正，最後說明為什麼「前端看到命中」不等於「伺服器認定命中」。

先說結論

魚群用「行為權重＋路徑約束」而不是純隨機；子彈與魚用圓形碰撞，快子彈要掃掠或子步；所有實體用固定上限的物件池；命中與派彩由伺服器依局單決定，前端只負責預測與演出。把這四件事分開，效能與公平性才不會互相拖累。

座標、時間步與可重現性

先決定邏輯座標，例如 1280×720，所有魚、子彈、砲台都用這個座標計算；繪製時再依實際 canvas 尺寸縮放。這樣不同裝置的遊戲行為一致，除錯時也只需要一組數字。若直接用 CSS 像素當邏輯座標，桌機與手機的魚速、碰撞半徑都會不同。

時間步建議用固定步長（例如 1/60 秒）搭配累加器，而不是直接把 deltaTime 餵給物理。固定步長讓碰撞與魚群行為可重播，也避免分頁回來時一次更新太大距離：

const STEP = 1 / 60;
let accumulator = 0;

function frame(now) {
  const delta = Math.min(0.05, (now - last) / 1000);
  last = now;
  accumulator += delta;
  while (accumulator >= STEP) {
    update(STEP);
    accumulator -= STEP;
  }
  render(accumulator / STEP);
  requestAnimationFrame(frame);
}

渲染可以用插值讓畫面滑順，但邏輯只認固定步長。若你的產品需要與伺服器重播同一局，還要把隨機種子、魚的生成時間、砲台角度與開火時間寫進局單，而不是只記錄結果。

魚群行為：Boids 的三個力

Boids 由三個基本力組成：

  • 分離（separation）：避免魚疊在一起。
  • 對齊（alignment）：讓附近魚的朝向趨於一致。
  • 聚合（cohesion）：往鄰居的中心靠攏。
function steer(fish, neighbors) {
  let sep = { x: 0, y: 0 }, ali = { x: 0, y: 0 }, coh = { x: 0, y: 0 };
  for (const other of neighbors) {
    const dx = fish.x - other.x, dy = fish.y - other.y;
    const d2 = dx * dx + dy * dy;
    if (d2 > 0 && d2 < 90 * 90) {
      sep.x += dx / d2; sep.y += dy / d2;
      ali.x += other.vx; ali.y += other.vy;
      coh.x += other.x; coh.y += other.y;
    }
  }
  const n = Math.max(1, neighbors.length);
  coh.x = coh.x / n - fish.x; coh.y = coh.y / n - fish.y;
  return {
    x: sep.x * 1.6 + ali.x / n * 0.5 + coh.x * 0.002,
    y: sep.y * 1.6 + ali.y / n * 0.5 + coh.y * 0.002,
  };
}

鄰居查詢不要用 O(n²) 掃全部魚。以 60 條魚為例還撐得住，但加上子彈與粒子就會吃緊。可以用格狀空間雜湊（spatial hash）把鄰近格子裡的魚取出，或限制每條魚只檢查固定數量的鄰居。對手機來說，限制鄰居數通常比最佳化數學更有效。

純 Boids 容易讓魚群散開或擠在角落，因此實務上會加「路徑約束」：每條魚有一個目標路徑（例如貝茲曲線或 waypoint），行為力只是微調，最終速度仍被拉回路徑切線。這樣魚群看起來自然，又不會偏離設計的表演區域。

生成與回收：物件池不是選項，是必需

捕魚機的實體生命週期很短：魚從左邊游出、被子彈擊中、播放金幣、消失。若每次都用 new Fish() 或建立 DOM，垃圾回收會週期性爆發，尤其在連續開火時。物件池的做法是預先配置固定數量，使用時取用，死亡時歸還並重設狀態。

class Pool {
  constructor(size, create) {
    this.items = Array.from({ length: size }, create);
    this.free = [...this.items];
    this.active = new Set();
  }
  acquire() {
    const item = this.free.pop();
    if (!item) return null;          // 上限保護，不無限生成
    this.active.add(item);
    return item;
  }
  release(item) {
    if (!this.active.delete(item)) return;
    item.alive = false;
    item.hit = false;
    this.free.push(item);
  }
}

上限保護很重要：如果場景需要 200 顆子彈，池就配置 200 顆；取不到時應該排隊或忽略，而不是偷偷 new。魚的數量也一樣，與其讓幾百條魚同時出現，不如用生成節奏控制密度。這會直接影響低階手機的幀率與伺服器同步量。

碰撞：圓形、掃掠與穿透修正

子彈通常是小的圓或膠囊，魚可以用一個較大的圓代表命中區。判定就是：

function circleHit(a, b) {
  const dx = a.x - b.x;
  const dy = a.y - b.y;
  const r = a.radius + b.radius;
  return dx * dx + dy * dy <= r * r;
}

若子彈速度是每秒 1200 邏輯單位，而幀率是 60fps，每幀移動 20 單位；魚的半徑可能只有 18 單位。此時只看「當前位置」仍有機會穿透。解法有兩種：

  1. 子步：把本幀位移切成 N 段，每段檢查一次。N 依速度與最小魚半徑決定，通常 2–4 段就夠。
  2. 掃掠圓：計算子彈從上一位置到目前位置形成的線段與魚圓的交點，取最早命中。

不論哪種，命中後都要把子彈標記為死亡並從 active 移除，避免同一顆子彈在同一幀擊中多條魚。若產品允許穿透彈，則要記錄已命中的魚 ID，不能只靠位置。

常見坑：縮放 canvas 後忘記同步碰撞半徑。視覺上魚變大了，碰撞圓還是舊的，玩家會覺得「明明打中卻沒中」。請把邏輯半徑與繪製縮放分開，並在 resize 時只改繪製比例。

砲台倍率與成本

砲台倍率通常代表「每發成本」與「命中後的派彩倍率」。例如 10 倍砲每發扣 10 點，命中魚後依魚的賠付表乘以砲台倍率。重點是：倍率不應該直接等於命中率。若高倍率同時提高命中率與派彩，期望值會偏離設計，甚至被玩家找出穩賺組合。

示範用砲台與魚種（僅供教學，不代表真實產品數學）
目標基礎賠付命中半徑速度備註
小丑魚2×16慢入門目標
河豚6×22中體型大、較易命中
鯊魚50×34快高賠付、出現率低
黃金龍200×40極快Boss，需伺服器判定

若每發成本是 bet，命中機率是 p，命中返還是 payout，則期望值約為 p × payout − bet。產品要讓這個值落在設計的 RTP 內，且要考慮子彈未命中的情況。這些計算必須用模擬與實際權重驗證，不能只看賠付表。

伺服器權威：前端只負責「看起來命中」

在真錢產品中，前端不能決定「是否命中」。正確流程是：

  1. 玩家按下開火，前端送出「砲台角度、倍率、時間戳、局單 ID」。
  2. 伺服器依自己的魚群狀態與 RNG 判定命中與否，扣成本、寫局單。
  3. 前端收到結果後播放命中或落空動畫；若延遲，先播放預測特效，但最終以伺服器為準。
  4. 結算時以局單 ID 冪等處理，避免重連後重複派彩。

如果前端先扣款、先播放命中，伺服器才非同步確認，會出現「畫面說中了、餘額卻沒加」的爭議。比較好的做法是：前端預測但不明確顯示最終結果，或顯示「結算中」；等伺服器回傳後再播放金幣與更新餘額。

另一種做法是「可驗證重播」：伺服器記錄魚的生成種子、初始位置、速度與開火時間，局後提供重播。玩家可以重算，但不需要相信前端。這比單純的 SHA-256 指紋更進一步，因為指紋只能證明「同一份資料」，不能證明「這份資料沒有被挑選過」。

效能：把預算花在看得見的地方

  • 背景快取：深海漸層、氣泡與光影畫到離屏 canvas，每幀只 drawImage。
  • 魚的繪製：若魚種固定，預先畫好各方向或使用 sprite atlas；不要在每幀重建路徑。
  • 粒子上限：金幣與水花用固定池，超過上限就淘汰最舊的。
  • 音效節流：連續命中時限制同時播放數量，或重用同一個 AudioNode。
  • 離屏更新：魚離開畫面立即回收，不要讓 active 陣列無限增長。

用 performance.now() 與 requestAnimationFrame 的 delta 建立簡單的幀率監看，但不要在正式環境顯示給玩家。若發現幀率低於 45fps，優先降低粒子數與鄰居查詢，而不是降低魚的碰撞精度。

無障礙與操作替代

捕魚機本質上是瞄準遊戲，對鍵盤與螢幕閱讀器不友善。至少應提供：

  • 鍵盤操作：方向鍵移動準星、空白鍵開火、數字鍵切換倍率。
  • 暫停功能：暫停時停止扣款與生成，不只是停止繪製。
  • 文字狀態：目前倍率、餘額、最近命中與剩餘子彈，透過 aria-live 公告。
  • 減少動態：關閉螢幕震動、粒子與快速閃光，保留命中文字。

若產品將捕魚機定位為娛樂而非競技，應在頁面明確標示「需要指標裝置」或提供自動捕魚模式；但自動模式仍要遵守成本與頻率限制，不能變成繞過操作的無限收益。

上線前檢查表

  • 邏輯座標與繪製縮放是否分離？碰撞半徑是否跟著縮放？
  • 子彈與魚是否有固定上限？池取不到時是否安全失敗？
  • 高速子彈是否使用子步或掃掠碰撞？
  • 同一顆子彈是否可能重複命中？死亡後是否立即移除？
  • 暫停、切到背景、重新連線時，魚群與子彈狀態是否一致？
  • 命中與派彩是否由伺服器決定？局單是否冪等？
  • 低階手機是否能維持 45fps 以上？粒子與音效是否有上限？

常見問題

捕魚機的魚群一定要用 Boids 嗎？

不一定。Boids 適合開放水域與自然群游；若產品需要固定陣形、路徑表演或低效能裝置，曲線路徑加區域生成會更可控。重點是魚群行為要可預測、可重播，而不是每幀都依賴大量隨機。

為什麼子彈要用圓形碰撞而不是像素碰撞？

子彈與魚的形狀會旋轉、縮放，像素級碰撞成本高且難以在伺服器重現。多數捕魚機用圓形或膠囊碰撞，搭配魚的命中半徑與子彈半徑；視覺上看不出差異，效能與一致性卻好很多。

高速子彈穿透魚怎麼辦？

使用連續碰撞（掃掠圓）或把每幀位移切成多個子步。只檢查當前位置會讓快子彈跳過魚；子步數可依速度決定，但要有上限，避免低幀率時一次做太多計算。

命中與否應該由前端決定嗎？

不應。前端可以播放命中特效，但真正是否命中、扣多少點、派彩多少必須由伺服器依局單與 RNG 決定。否則玩家可以修改程式或重放請求，直接影響收益。

砲台倍率越高越容易中嗎？

不一定。倍率通常影響每發成本與命中後的派彩，而不是直接提高命中率。若高倍率同時提高命中率，期望值可能完全改變；產品必須把成本、命中率與魚的賠付一起納入數學模型並用模擬驗證。
