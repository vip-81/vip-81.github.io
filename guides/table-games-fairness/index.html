百家樂、輪盤、21 點公平性：RNG、RTP、局單與斷線重連

賭桌遊戲的難點不是發牌動畫，而是「誰有權決定結果」與「斷線後如何恢復」。這篇先把三種遊戲的數學基準說清楚，再拆解前端指紋、伺服器 seed commitment、局單冪等與重連流程。

先說結論

RTP 是長期數學，不是單局保證；SHA-256 指紋只能證明資料一致，不能單獨證明公平；真正的公平需要伺服器持有 RNG 與牌靴、局前 commitment、局後 reveal、可重算的局單與冪等結算。重連時先查局單，不要讓前端自行判定成敗。

三種遊戲的數學基準

先把「理論值」與「單局結果」分開。下表是常見規則下的長期理論 RTP，實際產品會因牌數、抽水、賠付與規則細節而變動。

常見賭桌遊戲的理論 RTP（教學整理，非特定產品保證）
遊戲規則基準理論 RTP賭場優勢
百家樂 · 莊8 副牌、5% 佣金98.94%1.06%
百家樂 · 閒8 副牌、1:198.76%1.24%
百家樂 · 和8 副牌、8:185.64%14.36%
歐式輪盤單零 37 格97.30%2.70%
美式輪盤雙零 38 格94.74%5.26%
21 點6 副牌、S17、3:2、基本策略約 99.5%約 0.5%

這些數字不是「玩越久越接近」。它們是大量局數下的期望值；短期波動可能很大。百家樂的和局賠率高，但 RTP 明顯較低；輪盤的單號賠 35:1，但命中率只有 1/37，期望值與紅黑注相同。21 點則會因玩家策略而改變，基本策略的價值就是把可避免的錯誤降到最低。

百家樂：補牌規則是數學的一部分

百家樂的結果不是「誰點數大就贏」這麼簡單。閒家 0–5 補牌、6–7 停牌；莊家是否補牌取決於莊家點數與閒家第三張牌。這些規則是固定的，不能由玩家選擇，所以 RTP 可以在規則確定後精算。

莊家補牌規則（閒家已補第三張牌時）
莊家點數閒家第三張牌動作
0–2任意補牌
3非 8補牌
42–7補牌
54–7補牌
66–7補牌
7任意停牌
8–9任意自然，停牌

若閒家沒有補牌（6–7 或自然），莊家規則更簡單：0–5 補、6–7 停。實作時應把整張規則表寫成資料，並用單元測試覆蓋所有點數組合，而不是在流程中散落 if。一個常見錯誤是把「莊家 3 點對閒家 8」誤寫成補牌，長期會讓 RTP 偏離。

輪盤：37 格與「結果先定」

歐式輪盤的每個標準投注期望值相同：(命中格數 / 37) × 返還倍數。單號命中 1 格、返還 36 份，所以 36/37 ≈ 97.30%；紅黑命中 18 格、返還 2 份，36/37 也一樣。這就是為什麼「賠率越高越划算」是錯覺。

技術上，結果必須在轉輪動畫前決定。若讓球的物理模擬決定落點，幀率、背景暫停與裝置差異都會影響結果，無法聲稱公平。本專案先以 randomInt(37) 抽出結果，再用 animateTo(result) 把輪盤與球帶到對應格位；正式產品則把 randomInt 換成伺服器回傳的結果。

// 前端只負責播放；結果來自伺服器或已決定的局單
const { result, roundId } = await fetchRoundResult();
await animateTo(result);
settleBets(result, roundId);   // 以 roundId 冪等

21 點：牌靴、S17 與玩家決策

21 點的 RTP 不是固定值，會隨規則與玩家策略改變。6 副牌、莊家 S17、Blackjack 3:2、可加倍任意兩張、僅一次分牌，搭配完整基本策略，理論 RTP 約 99.5%。若把 Blackjack 改成 6:5，RTP 會下降約 1.4 個百分點；若莊家改 H17，又會再降一些。

牌靴要用 Fisher–Yates 洗牌，不能用 array.sort(() => Math.random() - 0.5)，因為這個比較函式不滿足傳遞性，分布會偏差。洗牌後把牌靴與索引存在伺服器；前端每次只拿到「自己應該看到的牌」，不能拿到整副牌靴，否則玩家可以預測後續牌。

function shuffle(deck, randomInt) {
  for (let i = deck.length - 1; i > 0; i -= 1) {
    const j = randomInt(i + 1);
    [deck[i], deck[j]] = [deck[j], deck[i]];
  }
  return deck;
}

分牌 A 的處理也要寫進規則：多數牌桌分 A 後每手只補一張就停牌，避免玩家取得多個 21 點。這些細節會影響 RTP 與玩家策略，不能等到上線後才補。

SHA-256 指紋：能證明什麼，不能證明什麼

本專案的百家樂與 21 點會對牌靴取 SHA-256 前 16 碼，顯示在側欄。它的用途是：

  • 確認重新整理前後是同一副牌靴；
  • 除錯時比對狀態；
  • 讓玩家知道牌靴內容沒有在本地被隨機替換。

但它不能證明：

  • 伺服器沒有在知道投注後才挑選牌靴；
  • RNG 沒有偏差或後門；
  • 牌靴沒有被事後替換成另一個「剛好」的版本。

指紋是完整性工具，不是公平性證明。把它當成「公平」會誤導玩家，也會讓工程團隊忽略真正需要的 commit-reveal 與稽核。

可驗證公平：commit-reveal 的正確用法

一個常見流程是：

  1. 伺服器產生 serverSeed，公開 SHA-256(serverSeed) 作為 commitment。
  2. 玩家提供或系統產生 clientSeed，並記錄 nonce。
  3. 以 HMAC(serverSeed, clientSeed + nonce) 產生隨機位元，映射到牌序或輪盤結果。
  4. 局後揭示 serverSeed，玩家重算雜湊與結果。
// 概念示意：實際映射需避免模數偏差
const bytes = await hmacSha256(serverSeed, `${clientSeed}:${nonce}`);
const value = new DataView(bytes).getUint32(0);
const result = value % 37;   // 正式版需拒絕取樣

commit-reveal 能防止「看到玩家下注後才換 seed」，但仍有前提：commitment 必須在投注前公開、serverSeed 不能重複使用、nonce 必須單調遞增、局單必須可稽核。若伺服器可以選擇何時揭示、或玩家看不到 commitment，這個機制就只是裝飾。

局單狀態機：避免重複派彩

一張桌遊局單至少要有以下狀態：created（已建立）、betting（接受投注）、locked（停止下注）、dealt（已發牌）、settled（已結算）、voided（作廢）。每次狀態轉移都要有時間戳與操作者，並且只能往前進。

created → betting → locked → dealt → settled
                         ↘ voided（僅限特定錯誤）

結算採冪等：settle(roundId) 第一次會寫入派彩與餘額，第二次直接回傳相同結果，不重複加錢。資料庫層可以用唯一鍵 (roundId, playerId) 或版本號做樂觀鎖。前端重連後只查詢局單，不自行推測。

斷線重連：三種遊戲的實務流程

百家樂

下注後斷線：重連時查局單。若已 locked 或 dealt，恢復牌局並等待結果；若仍 betting，允許取消或補下注（依產品規則）。不要重新發牌，也不要讓玩家重複下注。珠盤路與統計應由伺服器或可重建的事件日誌產生，不能只存在前端。

輪盤

下注後、開轉前斷線：恢復桌面投注與餘額。已開轉但未結算：查局單結果，直接播放結果，不重新旋轉。已結算：顯示結果與派彩，允許「重複上局」但建立新局單。前端 localStorage 只適合 demo；正式產品以伺服器為準。

21 點

玩家回合斷線：恢復手牌、目前手牌索引、莊家明牌與剩餘牌靴。若當時輪到莊家，重連後自動繼續補牌並結算；若已結算，顯示結果。最危險的是「前端已顯示加倍，但伺服器沒收到」：重連後必須以伺服器版本為準，並在 UI 說明差異。

設計原則：前端狀態是快取，不是真相。任何涉及餘額、投注、派彩的資料，都應以伺服器局單為權威；前端只負責呈現與送出意圖。

公平性與重連檢查表

  • RNG 是否由伺服器持有？是否有拒絕取樣避免模數偏差？
  • 洗牌是否用 Fisher–Yates？牌靴是否在投注前鎖定？
  • 是否在投注前公開 serverSeed 的 commitment？局後是否揭示？
  • 局單是否有唯一 ID、狀態機與時間戳？結算是否冪等？
  • 重連後是否只查局單，不重新發牌或重複派彩？
  • 前端指紋是否被正確描述為「完整性」而非「公平性」？
  • RTP 是否有模擬報告與版本紀錄？是否標明規則變體？
  • 是否有年齡驗證、限額、冷靜期與自我排除機制？

常見問題

百家樂的 RTP 是多少？

以標準 8 副牌、莊家 5% 佣金計算，莊注理論 RTP 約 98.94%、閒注約 98.76%、和局約 85.64%。實際值會依牌數、抽水與和局賠付變動，應以產品規則重新計算。

歐式輪盤的 0 號會影響 RTP 嗎？

會。單零輪盤有 37 格，所有標準投注的理論 RTP 都是 97.30%；美式雙零輪盤有 38 格，RTP 約 94.74%。多一個 0 直接增加賭場優勢。

SHA-256 牌靴指紋能證明公平嗎？

不能。指紋只能證明前後兩份資料相同，或協助除錯與重播；它不能證明牌靴沒有被挑選、伺服器沒有事後替換，也不能證明 RNG 沒有偏差。公平性需要 commit-reveal、局單與可重算流程一起成立。

什麼是 seed commit-reveal？

伺服器先公開 server seed 的雜湊（commitment），玩家提供 client seed；局後伺服器揭示 server seed，玩家可驗證雜湊與結果。這能防止伺服器在知道玩家投注後才換 seed，但仍需配合 nonce、局單簽章與稽核。

斷線重連最怕什麼？

重複派彩與重複下注。重連後必須以局單 ID 查詢結果，結算採冪等；前端不能因為沒收到回應就自行假設成功或失敗。若局單已結算，只恢復結果；若未結算，等待伺服器重播或補償。
