老虎機 FSM 與滾輪物理：停輪手感、連線判定與 Free Spin

老虎機看起來是「按一下、轉一轉、看有沒有中」，但真正難的是狀態：什麼時候可以再按、什麼時候該扣款、Big Win 演出期間能不能操作、免費遊戲剩下幾次。這篇用一個五狀態 FSM 把流程固定下來，再處理滾輪的重量感與賠付線判定。

先說結論

先決定結果，再播放動畫。滾輪用「等速滾動＋緩出停止＋小幅回彈」三段組成；賠付線用資料表而不是視覺位置推測；Free Spin 是獨立狀態，必須處理「免費遊戲中再次觸發」與剩餘次數；Big Win 是覆蓋層，不是一般結果文字。

為什麼用 FSM，而不是一堆布林值

一個可運作的老虎機至少有五個互斥狀態：idle（待機）、spinning（滾輪轉動）、evaluating（結算連線）、bigwin（演出）、freespin（免費遊戲）。用 isSpinning、isFreeSpin、isBigWin 三個布林值，很容易出現「正在 Big Win 但又按了旋轉」或「免費遊戲結束後餘額扣了兩次」的組合。

FSM 的好處不是程式碼比較漂亮，而是把「哪些操作合法」變成可檢查的表。以本專案的 StateMachine 為例，每個狀態只宣告自己能接受的事件：

const machine = new StateMachine("idle", {
  idle:       { on: { SPIN: { target: "spinning" } } },
  spinning:   { on: { REELS_STOPPED: { target: "evaluating", action: evaluateRound } } },
  evaluating: { on: { BIGWIN: { target: "bigwin" }, FS_START: { target: "freespin" }, END: { target: "idle" } } },
  bigwin:     { onEnter: showBigWin, onExit: hideBigWin,
                on: { CONTINUE: { target: "idle" }, CONTINUE_FS: { target: "freespin" } } },
  freespin:   { onEnter: enterFreeSpin, onExit: exitFreeSpin,
                on: { SPIN: { target: "spinning" }, END: { target: "idle" } } },
});

任何未宣告的事件都會被忽略，而不是偷偷改變狀態。這讓「旋轉中不能改注」、「Big Win 期間不能旋轉」、「免費遊戲由計時器自動推進」變成規則，而不是散落在事件監聽裡的 if。

實務提醒：FSM 只管理流程，不管理資料。餘額、投注、剩餘免費次數仍應放在獨立的 state 物件，並在每次轉移後持久化；不要把餘額塞進 FSM 的 context 後就忘記同步畫面。

結果先定：讓動畫只是演員

按下旋轉時，先做三件事：扣投注、抽出五輪的目標停位、把結果寫入本局紀錄。之後才啟動滾輪動畫。這樣做的好處是：

  • 低階手機掉幀時，結果不會跟著改變。
  • 切到背景再回來，可以直接跳到最終位置，不需要補完所有幀。
  • 正式產品可以改成「向伺服器要結果」，前端仍用同一個 animateTo(result)。
function prepareRound() {
  const stops = Array.from({ length: REELS }, () => randomInt(STRIP.length));
  const grid = stops.map((stop, reel) =>
    Array.from({ length: ROWS }, (_, row) =>
      STRIP[(stop + row) % STRIP.length]
    )
  );
  return { stops, grid };
}

注意 STRIP 是每個滾輪自己的符號帶。真實老虎機的滾輪長度與符號權重可能不同，甚至每個滾輪各有一條帶；不要用「從 0 到 N 隨機取一個符號」來模擬，否則賠付線的機率會與美術配置脫節。

滾輪物理：重量感從哪裡來

停輪手感通常由三段曲線組成，而不是單純的 linear：

  1. 加速段：0–120ms 從 0 拉到最大速度，避免一按就瞬移。
  2. 等速段：大部分時間維持固定速度，讓玩家看清楚符號流動。
  3. 緩出段：最後 500–700ms 用 ease-out 把速度收乾，停下前通常再加 4–8px 的回彈。
function reelOffset(elapsed, duration, distance, bounce) {
  const t = Math.min(1, elapsed / duration);
  const eased = 1 - Math.pow(1 - t, 3);       // easeOutCubic
  const base = distance * eased;
  if (t < 0.82) return base;
  const k = (t - 0.82) / 0.18;                 // 0 → 1
  return base + Math.sin(k * Math.PI) * bounce; // 停前小幅回彈
}

回彈必須只影響繪製位移，不能改變最終的符號索引。動畫結束後把 offset 歸零，否則連續旋轉會累積誤差，最後停位會偏一格。若使用 requestAnimationFrame 的 deltaTime，請把 delta 上限設在 50ms，避免分頁回來時一次跳過太多距離。

停輪順序也有講究：左到右依序停（例如每輪間隔 140ms）能製造期待感；但如果結果早已決定，停輪間隔不應影響結果。若你想做「接近大獎」的假張力，也必須確保最終停位與結果一致，不能為了好玩而讓某一輪多轉一圈後停在錯誤位置。

連線判定：從資料表開始

10 條賠付線不是「看起來橫的、V 形的」就好，必須把每條線的列索引寫成資料。例如 5×3 的線可以表示為 [1,1,1,1,1]（中間橫線）或 [0,1,2,1,0]（V 形）。判定時從第一輪開始：

function evaluateLine(grid, line, paytable) {
  const first = grid[0][line[0]];
  if (first === "scatter") return null;
  let count = 1;
  for (let reel = 1; reel < grid.length; reel += 1) {
    if (grid[reel][line[reel]] !== first) break;
    count += 1;
  }
  if (count < 3) return null;
  return { symbol: first, count, payout: paytable[first]?.[count] ?? 0 };
}

常見錯誤是用「整盤有幾個相同符號」來判定，這會把分散在不同輪、不同列的符號算成連線。另一種錯誤是允許 Wild 取代 Scatter，或讓 Scatter 從第二輪才開始算；這些都要依賠付表明確規定，不能靠猜。

賠付倍率是「投注的倍數」還是「總投注除以線數」？這是產品定義，必須寫在規則裡。本示範以「每線投注 × 賠付倍率」計算，並在 UI 顯示 總投注與線數，避免玩家誤解。

Free Spin：一個狀態，而不是一個計時器

免費遊戲的流程通常是：一般旋轉中出現 3 個以上 Scatter → 結算一般連線 → 顯示「Free Spin 觸發」→ 進入免費遊戲 → 每局自動旋轉 → 剩餘次數歸零 → 回到一般遊戲。這裡有兩個容易出錯的點：

  • 觸發與 Big Win 的優先順序：若同一局既有大獎又觸發免費遊戲，應該先播 Big Win，再進 Free Spin，或反過來？這是產品決策，但 FSM 必須只有一條合法路徑（本示範用 CONTINUE_FS）。
  • 免費遊戲中再次觸發：剩餘次數要加上新觸發的次數，而不是覆蓋。若用倒數計時器，容易在非同步結算時重複扣除。
function enterFreeSpin() {
  fsRemaining = 10;
  fsTotal = 0;
  freeRoundWin = 0;
  announce(`免費遊戲開始，共 ${fsRemaining} 次。`);
  scheduleFreeSpin();
}

function onFreeRoundSettled(win, retriggered) {
  fsTotal += win;
  freeRoundWin += win;
  fsRemaining -= 1;
  if (retriggered > 0) fsRemaining += retriggered;
  if (fsRemaining > 0) scheduleFreeSpin();
  else machine.send("END");
}

免費遊戲期間，投注按鈕與「補充籌碼」應停用；旋轉按鈕可以顯示「免費遊戲進行中」而不是可點擊。若玩家重新整理，免費次數與累積獎金必須能恢復，否則會產生「斷線就吃掉免費遊戲」的爭議。

Symbol 物件池與繪製策略

5×3 只有 15 個可見符號，物件池的收益不像彈幕遊戲那麼大，但仍有兩個好處：避免每局重建 15 個繪製物件，以及讓符號的動畫狀態（縮放、發光、位移）可以重設而不是重新配置。重點不是「池越大越好」，而是「固定上限、歸還時重設」。

class SymbolPool {
  constructor(size, factory) {
    this.free = Array.from({ length: size }, factory);
    this.active = [];
  }
  acquire() {
    const item = this.free.pop() ?? this.active[0];
    item.reset?.();
    this.active.push(item);
    return item;
  }
  releaseAll() {
    for (const item of this.active) this.free.push(item);
    this.active.length = 0;
  }
}

如果你用 DOM 畫符號，頻繁 innerHTML 反而比物件池更傷效能；此時應只更新文字與 class，或改用 Canvas。若用 Canvas，請把靜態符號預先畫到離屏 canvas，再 drawImage，不要每幀重畫路徑與漸層。

Big Win 分級與可存取性

Big Win 不是單純的「WIN」文字，而是依「本局贏得 ÷ 投注」分級：25× 以上 BIG WIN、50× 以上 MEGA WIN、100× 以上 LEGENDARY。分級只影響演出與音效，不應改變派彩。演出期間要：

  • 把背景內容設為 inert 或至少讓焦點鎖在對話框內；
  • 提供「繼續」按鈕，並支援 Escape；
  • 用 aria-live 公告最終金額，不要只靠動畫數字；
  • 尊重 prefers-reduced-motion，直接顯示最終金額。

本專案的 Big Win 對話框會在顯示後把焦點移到「繼續」，Tab 只在對話框內循環；關閉後焦點回到原本的旋轉按鈕。這些細節不影響數學，但會直接影響鍵盤與螢幕閱讀器使用者能否完成遊戲。

RTP、波動與「感覺」的區別

RTP 是長期返還率，波動（volatility）是結果分布的離散程度。高波動遊戲可能長時間不中，但中獎時金額較大；低波動則較常中小獎。兩者都可以有相同的 RTP。停輪回彈、Big Win 音樂與硬幣粒子只影響體感，不影響 RTP。

本示範不承諾固定 RTP，因為符號權重、滾輪帶與賠付表是教學用配置。正式產品必須以模擬（數億局）驗證實際 RTP、命中率與最大倍數，並把數學報告與版本號保存下來。前端 demo 的 crypto.getRandomValues 也不能取代伺服器 RNG 與簽章。

上線前檢查表

  • 結果是否在動畫前決定？重新整理後是否能恢復未完成的免費遊戲？
  • 旋轉中、Big Win 中、免費遊戲中，所有按鈕的 disabled 狀態是否一致？
  • 滾輪停位是否與結果索引一致？回彈後 offset 是否歸零？
  • 賠付線是否從第一輪連續判定？Wild／Scatter 規則是否寫進賠付表？
  • 快速連按旋轉是否會重複扣款？是否有 phase 或 FSM 保護？
  • 降低動態時是否跳過粒子與長時間倒數，但仍顯示結果？
  • 手機 320px 寬度是否仍能看到投注、餘額與結果？

常見問題

老虎機的停輪動畫會影響結果嗎？

不會。結果在旋轉開始前就由隨機來源決定，滾輪只是被動畫帶到目標位置。這樣即使裝置掉幀、切到背景或開啟減少動態，結果仍保持一致。

為什麼滾輪停下時要回彈？

回彈是視覺與音效的「重量感」設計，模擬機械滾輪的慣性。它只作用在顯示座標，不會改變最終停下的符號索引；實作上要在動畫結束後把位移歸零，避免累積誤差。

10 條賠付線要怎麼判定？

把每條線的 (reel, row) 座標寫成資料表，從第一輪開始取符號；若後續輪不符合就停止。只有從第一輪連續出現的組合才算連線，Scatter 通常不看線，而是計算全盤數量。

Free Spin 為什麼需要獨立狀態？

免費遊戲會改變投注扣除、剩餘次數、倍率與自動旋轉流程，也可能在同一次結果中再次觸發。把它做成 FSM 的獨立狀態，可以避免與一般旋轉的按鈕狀態、Big Win 演出和餘額結算互相污染。

Symbol 物件池真的有必要嗎？

若每幀都建立新物件與 DOM，垃圾回收會造成週期性卡頓。物件池預先配置固定數量並重複使用，能降低 GC 壓力；但在 5×3 且只重繪 Canvas 的情況下，效益主要來自避免配置，而不是池本身。
